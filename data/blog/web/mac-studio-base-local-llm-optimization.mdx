## 1. 시작하며: 현실적인 하드웨어와 로컬 AI의 벽

최근 로컬 환경에서 에이전틱 AI(Hermes 등)를 활용한 코딩 파이프라인을 구축해 운영하고 있다. 메인 코딩 모델로는 강력한 추론 성능을 가진 **Qwen 27B(4-bit)** 를 사용한다.

내가 사용하는 머신은 **Mac Studio (M5 Max, 통합 메모리 36GB)** 기본형이다.

<br />

```
Hardware Overview:
  Model Name: Mac Studio
  Chip: Apple M5 Max (18 Cores)
  Memory: 36 GB Unified Memory
```

<br />

물론 64GB나 128GB로 CTO 주문을 했다면 모든 것이 편안했겠지만, 하드웨어 옵션 비용에 수백만 원을 당장 태울 수는 없는 노릇이다. 개발자란 모름지기 **"주어진 자원의 한계 안에서 최적의 해답을 찾아내는 사람"** 아니던가?

하지만 36GB라는 통합 메모리는 생각보다 타이트했다. 특히 코딩 에이전트와 장시간 세션을 진행할 때 심각한 문제에 직면했다.

---

## 2. 문제의 발단: 27B + 3B 동시 상주와 Metal OOM

코딩용 LLM으로 긴 컨텍스트를 유지하고 빠른 응답 속도를 내려면 **프롬프트 캐시(`--prompt-cache-bytes 6GB`)** 는 절대 포기할 수 없는 최소한의 마지노선이었다.

단순 계산을 해보자:

* **Qwen 27B 4bit 가중치**: 약 15 GB
* **27B 프롬프트 캐시**: 6 GB
* **시스템 OS + 브라우저 + 개발 도구**: 약 12~14 GB
* ➡️ **벌써 33~35 GB를 점유**하고 있어 잔여 메모리는 2~3 GB에 불과하다.

이 상태에서 대화가 길어져 컨텍스트가 5만 토큰에 육박하면, Hermes 에이전트는 대화창 크기를 줄이기 위해 **컨텍스트 압축(`compaction`)** 을 트리거한다. 이전 대화 기록 수십~수백 턴을 보조 경량 모델(**Qwen 2.5 3B**)에 던져 깔끔한 인수인계 브리핑 문서로 요약하는 작업이다.

그리고 바로 그 순간, 터져버렸다.

```text
2026-10-04 19:33:26 - INFO - Prompt processing progress: 14294/14295
Exception in thread Thread-1 (_generate):
...
RuntimeError: [METAL] Command buffer execution failed: 
Insufficient Memory (00000008:kIOGPUCommandBufferCallbackErrorOutOfMemory).
```

요약해야 할 이전 대화 분량(약 14,300 토큰)을 3B 모델이 GPU로 한 번에 올리는(Prefill) 순간, 27B가 메모리를 쥐고 있는 상태에서 Metal GPU 버퍼 할당에 실패한 것이다.

결과는 참담했다. MLX 서버의 생성 스레드가 사망했고, Hermes는 응답을 기다리다 **5분(300초) 타임아웃(Stall-Interrupted)** 에 걸려 작업이 그대로 멈췄다.

## 3. 임시 방편의 한계: 클라우드 API(Gemini)와 쿼터 고갈

"로컬 GPU가 부족하면, 압축 작업만 Gemini Flash 같은 외부 클라우드 API로 넘기면 되지 않을까?"

처음에는 이 방법으로 급한 불을 껐다. Gemini는 Mac 메모리를 1MB도 쓰지 않으니 10만 토큰도 2~3초 만에 요약해 넘겨주었다.

하지만 곧바로 또 다른 현실의 벽을 만났다:

```text
Gemini HTTP 429 (RESOURCE_EXHAUSTED): You exceeded your current quota.
* Quota exceeded for metric: generate_content_free_tier_requests
```

에이전트 특성상 파일 수정, 테스트, 명령 실행 등을 반복하다 보면 컨텍스트가 수시로 압축 임계치에 도달한다. 무료 API 티어는 몇 번의 턴 만에 순식간에 동나버렸다. 

결국 진정한 자립을 위해서는 **100% 로컬 환경에서, 외부 의존성 없이 이 문제를 풀어내야만 했다.**

---

## 4. 유레카: "동시 상주"가 아니라 "순차 실행"이다

"27B 캐시 6GB를 줄이지 않으면서, 3B도 죽지 않게 만들 수는 없을까?"

고민을 거듭하다 에이전트의 내부 라이프사이클을 가만히 뜯어보았다. 그리고 중요한 사실 하나를 깨달았다.

> **"두 모델은 동시에 일할 필요가 전혀 없다."**

Hermes가 컨텍스트를 압축할 때의 흐름은 다음과 같다:
1. 대화가 임계치를 넘으면 **메인 모델(27B)의 턴 진행이 일시 정지**된다.
2. 압축 모델(3B)이 이전 대화를 요약하는 동안, **27B는 아무 일도 안 하면서 21GB의 메모리만 차지한 채 놀고 있다.**
3. 3B의 요약이 끝나면 비로소 27B가 그 요약본을 받아 다음 코딩 작업을 시작한다.

즉, **100% 순차적(Sequential)인 작업**이다.

게다가 Apple Silicon의 통합 메모리와 초고속 NVMe SSD는 15GB 크기의 27B 모델을 내리고 다시 올리는 데 **불과 0.6초~1초**밖에 걸리지 않는다.

그렇다면 답은 명확했다:
> **"압축할 때는 27B를 잠시 내쫓고(메모리 100% 해제), 3B가 36GB 전체를 여유롭게 쓰며 초고속 요약을 마친 뒤, 다시 27B를 불러오면 된다!"**

## 5. 아키텍처 구축: MLX Dynamic Model Swapper

이 아이디어를 바탕으로 Hermes와 MLX 서버 사이에 가벼운 비동기 프록시 매니저(`mlx_manager.py`)를 설계했다.

<br />

```
┌────────────────────────────────────────────────────────┐
│                      Hermes Agent                      │
└──────────────┬──────────────────────────┬──────────────┘
               │ (포트 1234: 메인 LLM)     │ (포트 1235: 컨텍스트 압축)
               ▼                          ▼
┌────────────────────────────────────────────────────────┐
│               MLX Dynamic Swapper Manager              │
│               (~/.mlx-server/mlx_manager.py)           │
├────────────────────────────────────────────────────────┤
│  [평소 상태]                                            │
│    • Qwen 27B 가동 (포트 18234)                        │
│    • 6GB 프롬프트 캐시 온전히 확보                      │
│                                                        │
│  [포트 1235 압축 요청 도착 시: 자동 스왑]              │
│    1. swap_lock 획득                                   │
│    2. 27B 프로세스 종료 (Metal 메모리 21GB 즉시 반환)   │
│    3. 3B 기동 (0.5초 만에 준비 완료)                   │
│    4. 36GB 단독 점유 상태로 1.5만 토큰 OOM 없이 요약  │
│    5. 요약 스트리밍 완료 즉시 3B 종료                  │
│    6. 27B 재기동 (0.6초 만에 캐시 로드)                │
│    7. swap_lock 해제                                   │
└────────────────────────────────────────────────────────┘
```

<br />

### 구현 시 반드시 챙겨야 했던 디테일들

단순히 끄고 켜는 스크립트만 작성하면 예상치 못한 버그를 만난다. 실제 구현에서 해결한 핵심 포인트들이다:

#### 1. SIGSTOP이 아니라 Process Kill이어야 하는 이유
처음에는 `SIGSTOP` 시그널로 27B를 일시정지시키면 어떨까 생각했다. 하지만 **macOS Metal 프레임워크는 프로세스가 완전히 종료되지 않는 한 통합 메모리(GPU 버퍼)를 반환하지 않는다.** 따라서 프로세스 그룹 전체를 깔끔하게 종료(`os.killpg`)해 메모리를 0MB로 만들어야만 했다.

#### 2. 무의미한 모델 스왑 방지 (Fast-path Health Check)
Hermes는 주기적으로 모델 생존 여부를 확인하기 위해 `GET /v1/models`를 찌른다. 만약 헬스체크 요청에도 모델을 교체한다면 계속해서 27B와 3B가 핑퐁을 치며 뻗게 된다. 
따라서 헬스체크는 프로세스를 띄우지 않고 **미리 캐싱된 JSON 메타데이터를 즉시 리턴**하도록 바이패스했다.

#### 3. 동시성 락(`swap_lock`)으로 502 에러 원천 차단
3B가 요약하는 몇 초 사이에 사용자의 추가 입력이 들어올 수 있다. 이때 27B 포트로 들어온 요청이 "서버 없음(502 Bad Gateway)" 에러를 받으면 Hermes는 "로컬 서버가 죽었다"고 착각해 외부 Fallback(Gemini)으로 탈출해 버린다.
이를 막기 위해 **3B 요약과 27B 복구가 끝날 때까지 1234 포트로 들어온 요청을 안전하게 대기(Queue)** 시키는 비동기 락을 걸었다.

## 6. 검증: 실제로 얼마나 걸릴까?

모든 세팅을 마친 뒤, 실제 Hermes API 호출을 통해 전 과정을 벤치마크했다.

```text
[MLX Manager] Compaction requested! Stopping 27B and starting 3B...
[MLX Manager] Stopping 27B-Main (PID: 71725) to release Metal memory...
[MLX Manager] 27B-Main stopped. Metal memory 100% freed.
[MLX Manager] Starting 3B on internal port 18235...
[MLX Manager] 3B compaction server is ready with full VRAM!
[MLX Manager] Compaction stream complete! Restoring 27B model...
[MLX Manager] Stopping 3B-Compaction (PID: 72184) to release Metal memory...
[MLX Manager] 3B-Compaction stopped. Metal memory 100% freed.
[MLX Manager] Starting 27B on internal port 18234...
[MLX Manager] 27B server is ready for inference!
[MLX Manager] 27B model restored successfully!
```

* **3B 기동 ➡️ 대용량 요약 생성 ➡️ 종료**: **3.26초**
* **27B 재기동 ➡️ 캐시 복원 ➡️ 추론 준비**: **3.14초**

개발자가 체감하는 대기시간은 불과 **6초 남짓**이다. 그 짧은 시간 동안 21GB가 증발했다가 다시 나타나며, 지긋지긋하던 Metal OOM 에러는 영구히 박멸되었다.

터미널에서 `mlx status`를 쳐보면 실시간 상태도 직관적으로 확인된다:

```text
MLX Dynamic Swapper: ONLINE (Manager PID: 83773)
  Main Endpoint:       http://127.0.0.1:1234/v1
  Compaction Endpoint: http://127.0.0.1:1235/v1

  Active Model:       Qwen3.8-27B-4bit (Main Coding Model)
  Status:             Running (PID: 11143, RAM: 14,668MB, Prompt Cache: 6GB)
  Path:               /Users/deokgoo/.mlx-models/Qwen3.8-27B-4bit
  Auto-Swap Mode:     Active (27B unloads on compaction, 3B runs, then 27B restores)
```

## 7. 마치며: 제약은 아키텍처적 사고를 낳는다

물론 128GB Mac Studio를 쓰면 이런 고민 없이 모델 서너 개를 동시에 띄워놓고 편하게 쓸 수 있다. 

하지만 금전적 이유든 환경적 이유든, **주어진 하드웨어 스펙이 제한적일 때 무작정 하드웨어 탓만 할 필요는 없다.** 문제의 근본 원인을 추적하고 시스템과 애플리케이션의 라이프사이클을 면밀히 분석하면, 생각보다 훨씬 우아하고 가벼운 아키텍처로 돌파할 수 있는 길이 열린다.

기본형 36GB Mac Studio에서 27B 대형 모델과 압축 파이프라인을 100% 로컬로 쾌적하게 굴리고 싶은 분들에게 이 글이 작은 힌트가 되기를 바란다.

## 로컬 모델로 상용 AI를 대체할 수 있을까

"로컬 모델로 Claude나 GPT를 대체할 수 있을까?"

개발자들끼리 이 이야기를 꺼내면 보통 두 가지 현실적인 반응이 먼저 나옵니다.

첫 번째는 **성능**입니다. 아무리 오픈소스 진영이 빠르게 발전했다지만, 복잡한 로직을 해결하는 Claude나 Codex 수준을 온전히 대체하기엔 아직 역부족이라는 지적입니다.
두 번째는 **비용**입니다. 쓸 만한 모델을 제대로 굴리려면 결국 수백, 수천만 원짜리 고스펙 머신을 맞춰야 할 텐데, 그럴 바엔 그냥 상용 API를 결제해서 쓰는 게 훨씬 싸게 먹히지 않냐는 현실적인 계산이죠.

둘 다 충분히 일리 있는 이야기입니다. 저 역시 비슷한 의구심을 품고 있었습니다.

그렇다면 2026년 4분기 초인 지금 시점에서는 이 질문에 어떤 대답을 할 수 있을까요?

지난 한 달 동안 36GB 기본형 Mac Studio를 매일 쓰는 메인 코딩 에이전트로 굴려보았습니다. 단순한 벤치마크 테스트가 아니라, 실제 업무 도구로 하루 종일 쓰면서 나름대로 치열하게 삽질해보고 얻은 현실적인 대답과 고민들을 정리해보려고 합니다.

## 왜 우리는 로컬에 관심을 가질까

Claude나 GPT, Gemini 같은 상용 모델들은 이미 압도적인 퀄리티를 보여줍니다. 빵빵한 하드웨어 스펙과 고도화된 캐시 레이어 위에서 최적화되어 돌아가기 때문에, 웬만한 작업은 답답함 없이 쾌적하게 처리할 수 있습니다. 당장은 매달 구독료나 API 비용을 내고 쓰는 게 가장 속 편하고 합리적으로 보이죠.

그런데도 왜 사람들은 로컬 모델에 꾸준히 관심을 가지고, 내 컴퓨터에서 직접 돌려보고 싶어 하는 걸까요?

가장 먼저 와닿는 건 역시 **보안과 프라이버시**입니다. 회사의 민감한 코드베이스나 개인 프로젝트의 핵심 로직이 외부 서버로 전송된다는 찜찜함은, 아무리 규정을 신뢰하려 해도 완전히 떨치기 어렵습니다. 내 머신 안에서 모든 연산이 완결된다는 심리적 안정감은 생각보다 큽니다.

두 번째는 **비용의 안정성**입니다. 수십 개의 파일과 터미널 출력을 실시간으로 주고받는 코딩 에이전트를 써보면, 도구 호출(Tool calling)이 몇 번만 반복되어도 수만 토큰이 순식간에 증발합니다. 한 달 API 비용으로 수십만 원이 우습게 빠져나가죠. 반면 로컬은 초기 머신 비용만 감당하면 호출 횟수가 늘어나도 추가 비용 걱정 없이 일정하게 굴릴 수 있습니다. 실제로 처음에는 메이저 LLM API로 프로토타입을 만들다가도, 사용량과 서비스 규모가 커지면서 비용 최적화와 통제권을 위해 오픈소스/자체 모델 파이프라인으로 선회하는 사례들이 나오는 것도 같은 이유입니다.

하지만 제가 생각하는 가장 매력적인 이유는 따로 있습니다. 바로 **내가 원하는 레이어를 직접 구축하고 디테일하게 튜닝할 수 있다**는 점입니다.

물론 이건 양날의 검입니다. 상용 API는 이미 인프라 최적화가 다 끝난 완성형 제품이지만, 로컬은 캐시 관리부터 모델 라우팅까지 세팅을 직접 고민해야 하니까요. 하지만 반대로 생각하면, 상용 모델에서 느끼던 그 쾌적함을 로컬 하드웨어에서도 어느 정도 체감할 수만 있다면 이야기가 달라집니다. 외부 플랫폼에 종속된 도구가 아니라, 내 작업 흐름에 완전히 밀착된 **진정한 의미의 '개인 에이전트(Personal AI)'**를 소유할 수 있게 되는 것이죠.

결국 사람들이 로컬에 계속 관심을 두는 이유는 단순한 장난감 차원이 아닙니다. "과연 내 책상 위의 머신으로 이 쾌적함을 어디까지 끌어올릴 수 있을까?"라는 현실적인 가능성을 시험해보고 싶은 열망 때문입니다.

## 실험 환경: 36GB 기본형 Mac Studio M5 Max

제가 세팅한 하드웨어 환경부터 가볍게 공유해보겠습니다.

머신은 Mac Studio(M5 Max, 통합 메모리 36GB) 기본형입니다. 18코어 CPU, **40코어 GPU, 초당 400GB가 넘는 메모리 대역폭**을 갖추고 있습니다. 최고 사양은 아니지만, 개발자 입장에서 현실적으로 고민해볼 만한 가격대의 스펙입니다. (맥미니에 램만 64GB로 올리면 400만 원 선인데, 대역폭과 칩셋 체급이 완전히 다른 맥스튜디오 깡통이 약 430만 원이라 이쪽으로 급선회한 사연은 [이전 글](/blog/web/mac-studio-base-local-llm-optimization)에 정리해두었습니다.)

이 머신에서 코딩 에이전트를 실무 수준으로 굴리기 위해 선택한 핵심 전략은 두 가지였습니다.

**첫 번째는 네이티브 MLX 프레임워크의 사용입니다.** Ollama나 LM Studio 같은 llama.cpp 기반 툴 대신 Apple의 MLX 프레임워크를 직접 사용했습니다. `mlx_lm.benchmark`와 `llama-bench`로 대용량 프롬프트 처리량을 비교해보니 체감 차이가 생각보다 훨씬 컸습니다.

1. **압도적인 프리필(Prefill) 처리 속도**: 코딩 에이전트는 수만 토큰에 달하는 소스 코드와 컨텍스트를 한 번에 모델에 밀어 넣어야 합니다. llama.cpp 기반 엔진은 긴 컨텍스트(20K~40K)를 읽어 들일 때 Metal 연산 효율이 떨어져 프리필 단계에서 한참 멈칫거렸습니다. 반면 통합 메모리 버스에 최적화된 **네이티브 MLX**는 400GB/s 대역폭을 온전히 활용하며 초당 수백~수천 토큰의 프리필 속도를 뽑아냈습니다.
2. **조용한 작업 환경**: Ollama로 대용량 코드를 밀어 넣으면 팬이 거세게 돌기 시작했는데, 네이티브 MLX로 전환한 뒤에는 긴 컨텍스트를 읽을 때도 팬 소음이 거의 느껴지지 않을 만큼 안정적이었습니다. 책상 위에서 하루 종일 켜두는 머신에서는 결코 사소한 장점이 아니었습니다.

**두 번째는 MoE(Mixture of Experts) 모델의 활용입니다.** 메인 모델로 `Qwen3.6-35B-A3B-4bit`를 올렸습니다. 전체 파라미터는 350억 개지만, 토큰을 계산할 때 활성화되는 파라미터는 **30억 개(Active 3B)** 수준입니다. 덕분에 **35B급의 지능을 3B급의 빠른 속도(초당 45+ 토큰)**로 뽑아낼 수 있습니다. 비슷한 체급의 Dense 모델이 초당 12~15토큰에 머무는 것과 비교하면, 체감 반응 속도에서 오는 답답함이 완전히 사라집니다.

정리하자면 **36GB Mac Studio + 네이티브 MLX + MoE 모델**이라는 조합으로 현실적인 로컬 에이전트 환경을 꾸렸습니다.

## 실제로 체감한 로컬의 명확한 장점

한 달 동안 매일 작업에 써보면서 느낀 로컬의 장점은 확실했습니다.

1. **비용 걱정 없는 무제한 호출**: 코딩 에이전트는 사소한 수정에도 수십 번의 도구 호출을 반복합니다. 상용 API였다면 매달 눈덩이처럼 불어났을 비용이지만, 로컬은 머신 구매 이후 추가 한계 비용이 전혀 들지 않습니다. 많이 굴릴수록 본전을 뽑는 구조입니다.
2. **온전한 코드 보안과 심리적 안정감**: 회사의 프로덕션 코드나 아직 공개되지 않은 개인 프로젝트의 로직이 단 한 줄도 머신 외부로 나가지 않습니다. 외부 서버에 코드를 올려야 한다는 찜찜함이 근본적으로 사라집니다.
3. **긴 컨텍스트 인제스트의 쾌적함**: 네이티브 MLX 덕분에 대용량 소스 코드를 프롬프트로 밀어 넣을 때의 지연 시간이 대폭 줄었습니다. 코딩 에이전트 환경에서는 이 프리필 속도가 생산성에 직결됩니다.
4. **외부 제약으로부터의 자유**: API 호출 한도(Rate limit), 네트워크 불안정, 플랫폼 정책 변경이나 요금 인상 같은 변수를 신경 쓸 필요가 없습니다. 내가 원할 때 원하는 만큼 돌릴 수 있습니다.

## 솔직히 느낀 한계와 아쉬운 점

그렇다고 로컬 환경이 무조건 장밋빛인 것은 아닙니다. 한 달 동안 겪은 분명한 한계들도 있었습니다.

1. **더 큰 모델을 위한 하드웨어 장벽**: 36GB 기본형(약 430만 원)은 35B MoE 모델 하나를 쾌적하게 띄우기에 딱 맞는 마지노선입니다. 70B 이상의 대형 모델이나 긴 컨텍스트, 혹은 여러 모델을 동시에 메모리에 상주시키려면 64GB나 128GB 이상의 머신이 필요해지고, 이 경우 장비 비용이 1천만 원 가까이 훌쩍 뜁니다.
2. **프론티어 모델과의 추론력 격차**: 복잡한 아키텍처 설계나 다단계 추론, 미묘한 동시성 버그를 잡는 영역에서는 Claude 3.5 Sonnet 같은 최신 상용 모델이 여전히 한두 체급 위의 성능을 보여줍니다. 로컬 모델 단독으로는 아직 풀기 버거운 영역이 분명히 존재합니다.
3. **직접 감당해야 하는 세팅과 최적화의 수고**: 상용 API는 결제만 하면 바로 쓸 수 있지만, 로컬은 프레임워크 선택, 양자화 모델 테스트, 메모리 한도 튜닝을 모두 직접 해야 합니다. 실제로 저 역시 36GB 메모리 안에서 여러 작업을 돌리려다 커널 패닉을 몇 차례 겪었고, 이를 해결하기 위해 자체 스와퍼 스크립트까지 만들며 삽질해야 했습니다.

## 결국 대체가 아닌 '레이어드 아키텍처'의 문제

한 달간의 삽질 끝에 내린 솔직한 결론은, **"로컬이 상용 AI를 대체할 수 있는가?"라는 질문 자체가 이분법적 함정**이라는 점이었습니다.

진짜 중요한 질문은 대체 여부가 아니라, **"어떤 작업에 어떤 모델을 배치할 것인가"**입니다.

이 생각에 확신을 준 계기가 있었습니다. 바로 `sensami`라는 음성 AI 앱을 뜯어보았을 때였습니다. 기존에는 하나의 똑똑한 거대 모델이 처음부터 끝까지 모든 답변을 처리해야 한다고 생각했습니다. 하지만 sensami는 완전히 다른 방식으로 작동하고 있었습니다.

가볍고 빠른 소형 모델을 앞단에 두어 사용자의 의도를 실시간으로 1차 해석(80%)하고, 그 뒤에서 더 무겁고 정교한 모델이 문맥의 모호함을 보정(20%)해 최종 응답을 완성하는 **'레이어드 아키텍처(Layered Architecture)'**였습니다. 하나의 무거운 모델로 긴 지연 시간을 견디는 대신, 역할을 쪼개 층을 쌓으니 비교할 수 없을 만큼 빠르고 매끄러운 경험이 만들어졌습니다.

코딩 에이전트 역시 마찬가지였습니다.

- **고빈도·반복 작업과 파일 탐색, 코드 수정(전체 작업의 80%)**: 반응 속도가 빠르고 비용 부담 없는 **로컬 MoE 모델**에 맡깁니다.
- **복잡한 아키텍처 설계와 까다로운 디버깅(나머지 20%)**: 최고의 지능을 가진 **상용 프론티어 모델**로 라우팅합니다.

이렇게 역할을 나누어 계층화하면, 굳이 1천만 원짜리 고스펙 하드웨어를 맞추지 않고도 36GB 기본형 Mac Studio 위에서 상용 서비스 못지않은 생산성을 뽑아낼 수 있습니다. MoE로 속도를 챙기고, 스와퍼로 메모리를 아끼며, 필요한 순간에만 상용 API를 부르는 구조를 만드는 것이죠.

## 마무리하며

다시 처음의 질문으로 돌아가 봅니다. 로컬 모델로 상용 AI를 대체할 수 있을까요?

완전한 대체는 아니더라도, **일상적인 개발 작업의 상당 부분에서는 이미 충분히 현실적인 대안**이 되었습니다. 특히 비용 절감과 프라이버시, 빠른 반응 속도라는 측면에서는 로컬만의 확실한 강점이 존재합니다.

처음에는 단순히 매달 나가는 API 비용을 좀 아껴보자는 생각으로 시작한 삽질이었습니다. 하지만 한 달간 매일 부딪치며 얻은 가장 큰 소득은, 외부 플랫폼에 휘둘리지 않고 **내 작업 환경에 맞게 직접 조율하고 통제할 수 있는 나만의 자율 인프라를 갖추게 되었다는 점**입니다.
